# Architectural review — CLI, MCP server, init wizard

**Scope**: `packages/gnosis/src/cli/**` (incl. `src/cli/wizard/`), `packages/gnosis/src/mcp/*`, read against `packages/gnosis/README.md` and `packages/gnosis/CONFIGURATION.md` as the documented contract. Root-level engine modules were read only where the CLI's use of them is the subject.

**Method**: `grep -n "^export"` for structure, `Read` for behaviour, three live CLI invocations to confirm flag-scope behaviour (`npx tsx packages/gnosis/src/cli/main.ts doctor --rerank-pool 5 / --no-prf / --golden-set …`, each exit 0). Every claim below cites a file and a symbol.

**Size**: CLI layer ≈ 11 200 lines across 27 files, of which the wizard is 3 758 (14 files) and `retrieveCommand.ts` alone is 2 254. MCP is 452 lines across 3 files.

---

## Verdicts

| # | Expectation | Verdict | One-line basis |
|---|---|---|---|
| 1 | **Wizard understandable for an average user** | **adequate** | The scaffolding is excellent — sectioned screens, plan-before-write, probe-before-configure, measured-not-quoted advice — but the happy path still routes an average user through two 7-row expert menus (`ANALYZER_CHOICES`, `ADAPTER_CHOICES`) whose answer the wizard has already computed, and the amend menu silently cannot reach two answers it appears to cover. |
| 2 | **Interface consistency** (flags, output shapes, exit codes) | **strong**, with one confirmed hole | README's flag table is test-locked (`tests/readmeFlags.test.ts`) and matches `args.ts:FLAGS` 1:1; commands match across `cli.ts:COMMANDS` / `help.ts:helpText` / README. But three flags escape `cli.ts:SCOPE_CHECKS` and are silently accepted-and-ignored on every command — the exact failure `args.ts`'s own docblock exists to prevent. |
| 3 | **Clean code, meaningful naming** | **strong** | Small named functions, discriminated-union results, no `any`, no classes; docblocks explain *why* and cite the measurement or the incident that produced the rule. Readable without investigation almost everywhere. |
| 4 | **Modularity — thin CLI over a library** | **weak** | Inverted: `src/index.ts:search` and `src/mcp/server.ts:runAnswer` are both **argv-string clients of the CLI**. Retrieval policy (rerank pool floor, relevance floor, budget, confidence) lives in `src/cli/retrieveCommand.ts` — a 2 254-line command file — so no consumer can reach it except by marshalling strings. The MCP server *is* a thin second consumer (good), but of the CLI, not of a library. |
| 5 | **Functional style / minimalism** | **strong** style, **adequate** minimalism | Effectively zero `let`/`for`/mutation in the reviewed surface; `reduce`/`map`/recursion throughout; `readonly` everywhere. Minimalism is the weaker half — `retrieveCommand.ts` and `rerankFlow.ts` (940 lines) are past the size where a single file is one responsibility. |
| 6 | **Production readiness** | **strong** | Refusals name their remedy nearly universally; `main.ts` cannot emit a stack trace for the two error classes that were escaping (`cli.ts:contextResult`, `cli.ts:withContext`); the download path verifies sha256 before promoting a `.part`; the reranker is never configured on an HTTP 200 alone. Residual gaps are narrow and listed below. |

## Wizard walkthrough — as an average user

I walked `wizardCommand.ts:interview` → `wizard/flow.ts:askCorpus` → `wizard/rerankFlow.ts:askRerank` → `wizardCommand.ts:review` in order, reading the literal strings each step prints.

### Entry

`runWizardCommand` refuses without a TTY. Verified live:

```
$ dp-gnosis wizard < /dev/null            # exit 2
wizard needs an interactive terminal — it asks questions, and reading EOF as an
answer would half-configure this machine in silence; use `npm run gnosis -- init
<dir…>` and `npm run gnosis -- setup`, which are the scriptable path
```

Good refusal: names the fault, the reason, and two working alternatives.

With a TTY, `screen.ts:banner` draws a box, then `WELCOME` (`wizardCommand.ts`) sets the contract up front:

> dp-gnosis setup. No profile and no config is written until you confirm the summary at the end, so Ctrl-C before it leaves your configuration untouched. Two things asked for along the way DO outlive an abort: a model file you agree to download, and a server you agree to start. Both are named as they happen.

This is the single best thing in the wizard. The user knows the escape hatch and its two exceptions before answering anything.

### 1/6 — Where things go

`ROOT_EXPLANATION`:

> Everything dp-gnosis builds lives under one data root — the atoms your documents are split into, the search index, any reranker model downloaded here, and the server log.
> Your own documents are never moved, written to or modified. They are only read.

Then `Data root` (input, pre-filled with `dataRoot()`). One keystroke (Enter) to accept. Excellent: the second sentence answers the question an average user is actually anxious about.

**Issue (F6).** `instanceRefusal` runs *after* this question. Its first half — "a profile already exists" — depends only on `userProfilePath()` and is knowable before anything is asked, so a re-run of the wizard spends a question before refusing.

### 2/6 — What to index

`CORPUS_EXPLANATION` explains corpus directories, symlink following, and domain labels in three plain sentences. Then:

- `Corpus directory (absolute, or ~/…)` — input, **no default**
- `Domain label for <path>` — input, defaults to the directory's own name
- `Add another corpus directory?` — confirm, default no

Validation is immediate and the messages are good (`flow.ts:pathProblem`, `emptyProblem`):

> that path is relative — write it in full, or start it with ~/, so the scope cannot move with the shell
> /x holds no markdown within 4 levels — an ingest over it would walk nothing, and a silently empty corpus is how a vault comes to answer nothing while every check stays green

On success: `found at least 37 markdown files in /path — the check stops at 4 levels deep, so a deeper tree holds more`. Honest about the bound.

**Issue (F2, high).** `flow.ts:askRoot` recurses unconditionally on any invalid answer and offers **no way out**. There is no "blank to cancel" affordance, so a user who mistypes a path they cannot correct — or who launched the wizard by accident — can only Ctrl-C. This is precisely the trap `rerankFlow.ts:askPort` documents having already been fixed once ("the only way out was Ctrl-C — which discards the download that has already been paid for"); the lesson was not carried back to `askRoot`.

Then the `.gitignore` offer, per file (`flow.ts:askOffer`), with an honest explanation of what cannot be translated:

> 12 of its lines are plain paths and can be skipped; 5 cannot be used — a blank, a comment, a wildcard or a negation is not expressible as a path prefix, which is all an exclusion is.

Everything pre-checked, unchecking declines. Then `Paths to skip inside those directories, comma separated (blank for none)`.

### 3/6 — How documents are labelled

`TYPES_EXPLANATION` is clear, and the second paragraph is exactly the reassurance needed:

> Hiding a type is a DISPLAY default only — those documents are still ingested and still indexed, and `--include-history` brings them back into results.

Two prompts, both pre-answered with shipped defaults. Enter, Enter.

### 4/6 — How text is matched

This is where the average user falls off. The sequence is:

1. `What language are the documents mostly in?` — English / Hungarian. Clear.
2. `Do they contain code identifiers — flags, snake_case names or dotted paths?` preceded by `advice.ts:IDENTIFIER_ADVICE`, which correctly states that the measured sign is *opposite* on the two languages. Clear.
3. The preset table, then `Which of these fits you?` — `fast` / `balanced` / `quality (recommended)` / `custom`. Clear, and `preset.ts:presetTable` renders a real comparison with a Hungarian footnote.
4. `→ recommended chain: porter-fold`
5. **`Analysis chain`** — a 7-row menu (`advice.ts:ANALYZER_CHOICES`), each row carrying a `when` clause, a pro and a con.
6. **`Ranking adapter`** — a 7-row menu (`advice.ts:ADAPTER_CHOICES`), of which **four** are rows the copy itself tells the user not to pick: *"Pick this only if you are running an experiment; it is not a route to search with"* (×2), *"Pick this only to reproduce the LanceDB comparison it was built for"*, *"Pick this only to reproduce the larger-pool experiment it records"*.

**Issue (F1, high).** Steps 5 and 6 ask, in retrieval jargon, a question the wizard has just answered in plain language. `PRESET_EXPLANATION` states the design intent explicitly:

> A preset answers the rest of the interview for you. It only PRE-SELECTS a row each menu already offers — every question is still asked, every row is still choosable…

Those two sentences contradict each other from the reader's chair: the preset promises to answer, then asks everything anyway. For a repo author this is correct and desirable; for the stated audience it is two dense expert screens with no value added over the recommendation already printed. Four adapter rows are actively user-hostile — the wizard is offering a `lancedb-vec` route that `handbook/GNOSIS-GUIDE.md` records as **measured harmful** (−0.1621 nDCG@10 on `vault`).

Then `Serve pseudo-relevance feedback by default?` with a genuinely good two-line pro/con (`advice.ts:PRF_ADVICE`) that explains RM3 without naming it.

### 5/6 — Reranking

The best-engineered section. `RERANK_ADVICE` + `EXISTING_SERVER_NOTE` set expectations before the first question, and the ladder is:

`Set up the reranker?` → search `candidateUrls()` → probe each rerank-named id → if one passes, `A working reranker is already running. Use it, or set up your own?` (recommended: use it) → `How many candidates should the reranker reorder?`.

If nothing answers: `Which reranker?` → `Which quantisation?` → possibly the `node-llama-cpp` install offer (defaulted to **no**, with the 764 MB cost and the `package.json` rewrite stated first) → `How should the model be run?` → `Download <file> (2.32 GB) into <dir>?` → port resolution → `Start it now?  llama-server -m … --reranking --pooling rank …` → probe → pool depth.

Three things here are exemplary and worth preserving verbatim:

- **Nothing is configured on an HTTP 200.** `rerankFlow.ts:servedRung` / `localRung` both end in `rerankHealth`, and the docblock explains the missing-`cls.output.weight` failure that motivates it.
- **`NO_ROUTE` is checked before the download.** The docblock records that the order was previously download-then-decide and produced two contradictory messages after a multi-gigabyte fetch.
- **`timingLines` measures this machine** instead of quoting a constant, and labels the pool projection as a projection.

**Issue (F3, medium).** `rerankFlow.ts:serveModel` and `resolveRunMode` gate on `backend.kind === 'llama-server'` only, while `backend.ts:BACKEND_KINDS` detects three. A machine with `llama-swap` or `ollama` on PATH and no bare `llama-server` is told:

> No llama.cpp server was found on PATH, so the model cannot be started from here.
> Install llama.cpp (or llama-swap), then serve the file with: `llama-server -m …`

— advice naming a tool the user already has, plus a command that will not run. `ollama` is detected and never consumed anywhere.

**Issue (F7, low).** `rerankFlow.ts:fetchModel` prints `the download did not verify and was discarded: <error>` for *every* `downloadFile` failure, including `diskCheck`'s "not enough free disk" and `openBody`'s "answered HTTP 404" — neither of which is a verification failure, and both of which have different remedies.

**Issue (F8, low).** `fetchModel` resolves the file by `file.toLowerCase().includes(quant.label.toLowerCase())` and takes the first match. `F16` substring-matches an `mmproj-f16.gguf`; a split `-00001-of-00002` GGUF would match part 1 and verify cleanly against its own size and oid while being unloadable.

Then the chat hops (`askChatModels`). `CHAT_NOTE` is honest about why there is no probe, and `OTHER_ADDRESS` refuses to write ids from an address the hops cannot reach — a genuinely subtle correctness guard.

### 6/6 — Build, summary, decision

`BUILD_EXPLANATION` states what confirming starts, and explicitly that enrichment is *not* part of it. Then `summaryOf` prints the three file paths and the literal JSON that will be written, then:

> Write it?  → Write it / Change an answer / Cancel

The three-way `select` (rather than a `confirm`) is the right call and the docblock records why.

**Issue (F4, high).** `wizard/amend.ts:AMENDMENTS` offers five rows: corpus directories, paths to skip, atom types, **"How text is matched"**, reranker pool. `amendMatching` calls `flow.ts:askMatching`, which re-asks language → identifiers → preset → **analysis chain** and returns. It does **not** re-ask the **Ranking adapter** or the **PRF** question — both of which are asked by `askCorpus` *after* `askMatching` returns and therefore appear on screen **under that same `4 / 6 · How text is matched` heading** during the first pass. A user who picked the wrong adapter and chooses the one menu row that visibly covered it gets four questions re-asked and their adapter silently unchanged. `amend.ts:NOT_AMENDABLE` names only the data root and the reranker setup, so the module's own stated rule — *"the menu says why rather than leaving them silently absent"* — is violated for exactly two answers.

On `Write it`, `commit` writes the instance and config, runs `ingest` then `index` with two-line narration each, writes `ingest-report.txt`, then runs one real `search --json` and reads `indexState`. The closing screen distinguishes `ready` from every other state and attaches a remedy per state (`STATE_REMEDY`). This is the strongest single design decision in the file: it closes the landmine `handbook/GNOSIS-GUIDE.md` names first.

**Issue (F5, medium).** `nextSteps` prints:

```
  dp-gnosis search "<keywords>" --adapter fts5 --profile /home/…/user.profile.json
  dp-gnosis doctor --profile /home/…/user.profile.json
```

Both flags are redundant on the instance just created: `paths.ts:ingestProfilePath` already **prefers** `userProfilePath()` when it exists, and `fts5` is `DEFAULT_ADAPTER`. The wizard's parting message teaches an average user that every future command needs a 70-character suffix.

**Issue (F9, medium).** Cancelling at the summary returns `refuse(CANCELLED_TEXT)` → `EXIT_PARTIAL` (3). `outcome.ts` defines 3 as *"real output was produced AND something was refused"*; a cancellation produced nothing. A scripted caller cannot distinguish "the user said no" from "the index build broke", both of which are exit 3 from this command.

### `init` / `setup` / `wizard` division — verdict

**The division is sound and each command's docblock justifies it**, but it is under-signposted.

| Command | Role | Judgment |
|---|---|---|
| `wizard` | guided, interactive, composes the other four | correct — it *composes*, it does not reimplement (`wizardCommand.ts:buildSteps` shells `ingest`/`index` through `runCli`) |
| `init` | scriptable profile creation | correct, and its refusals mirror the wizard's |
| `setup` | reranker backend, non-interactive, instance-independent | correct — it is a property of the machine, and `cli.ts:ROOTLESS_COMMANDS` reflects that |

Two signposting defects:

- `locations.ts:repoRootRefusal` — the first refusal an installed-package user will hit — names `init <dir>` and **not** `wizard`, although README:82 calls `wizard` *"the one command a fresh clone can start from"* and `cli.ts:ROOTLESS_COMMANDS` exempts it for exactly that reason.
- `help.ts:helpText` lists `init` before `wizard`; `cli.ts:COMMANDS` and README both lead with `wizard`.

## Findings by severity

### High

**F1 — `wizard/flow.ts:askMatching` + `askCorpus`: the preset does not spare an average user the two expert menus.**
*What*: after the preset pre-selects, `pick(prompter, 'Analysis chain', ordered(ANALYZER_CHOICES, …))` and `pick(prompter, 'Ranking adapter', ordered(ADAPTER_CHOICES, …))` still present 7 rows each. Four adapter rows are self-described as experiments not to be used, one of them (`lancedb-vec`) measured harmful on the product corpus.
*Why it matters*: this is the stated primary expectation. The two screens add no information over the recommendation already printed (`→ recommended chain: porter-fold`) and are the densest jargon in the interview.
*Recommendation*: collapse both to a `confirm` when a non-`custom` preset is active — `Use porter-fold (recommended)?` — with a "show all options" escape row that opens today's menu; keep the full menus unconditional under `CUSTOM_PRESET`. This preserves the design rule (`preset.ts` docblock: a preset may only move a cursor, never close a door) while making the door one keystroke rather than a screenful.

**F2 — `wizard/flow.ts:askRoot`: unbounded re-ask with no exit.**
*What*: `askRoot` recurses on every invalid path with no blank-to-leave affordance; the only exit is Ctrl-C.
*Why*: `rerankFlow.ts:askPort` records this same defect being fixed once ("pressing Enter re-submitted it forever and the only way out was Ctrl-C"). At `askRoot` the cost of Ctrl-C is low (nothing is written yet), but the first corpus root is the *first substantive question* of the wizard, so it is where an average user is most likely to be stuck.
*Recommendation*: accept a blank answer on the first ordinal as "cancel the wizard", mirroring `askPort`'s `PORT_DECLINED`, and state it in the prompt text.

**F3 — `cli.ts:SCOPE_CHECKS`: three flags escape scoping and are silently accepted on every command.**
*What*: `RERANK_POOL_FLAG` (`--rerank-pool`), `NO_PRF_FLAG` (`--no-prf`) and `--golden-set` are absent from `RETRIEVAL_FLAGS` / any scope list. `-k` is in the same class. Verified live:

```
$ dp-gnosis doctor --rerank-pool 5 --json   → exit 0, flag ignored
$ dp-gnosis doctor --no-prf --json          → exit 0, flag ignored
$ dp-gnosis doctor --golden-set /tmp/x.json → exit 0, flag ignored
$ dp-gnosis doctor -k 9 --json              → exit 0, flag ignored
```

*Why*: `args.ts`'s own docblock states the rule this breaks — *"an UNKNOWN flag is a hard error, never an ignored token… a silently dropped `--jsn` gives an agent-driven caller a wrong answer under a success code, which is the single worst failure mode a CLI driven by an LLM can have."* `cli.ts`'s scope docblock makes the same promise for misplaced flags. `--rerank-pool` and `--no-prf` are retrieval tuning knobs, and README:78 documents `--golden-set` as `bench`-only. A caller who writes `dp-gnosis ingest --no-prf` gets exit 0 and a wrong mental model.
*Recommendation*: add `RERANK_POOL_FLAG` and `NO_PRF_FLAG` to `RETRIEVAL_FLAGS`; add a `BENCH_ONLY_FLAGS = ['--golden-set']` check and a `misplacedBenchFlag` entry in `SCOPE_CHECKS`; decide explicitly whether `-k` is global (it is honoured by `search`, `ask`, `demo`) and scope it to those three if not. Lock the whole vocabulary with a test asserting every `FLAGS` key is either global-by-name or reachable from exactly one scope list — the current gap exists because scoping is a hand-maintained parallel list with no completeness check.

**F4 — `wizard/amend.ts:amendMatching`: two answers are silently unamendable under a menu row that appears to cover them.**
*What*: `askMatching` returns `{language, preset}`; `askCorpus` asks the **Ranking adapter** and the **PRF** confirm after it, under the same printed `4 / 6 · How text is matched` heading. Amending "How text is matched" therefore re-asks four questions and leaves the adapter and PRF untouched, and `NOT_AMENDABLE` does not mention them.
*Why*: the module docblock makes "the menu says why" its explicit contract. A user amending after seeing `"adapter": "minisearch"` in the summary has no path to change it except Ctrl-C and a full re-run.
*Recommendation*: either move the adapter + PRF questions inside `askMatching` (so `amendMatching` genuinely re-asks the whole section), or add them as their own `Amendment` rows. The first is closer to what the screen already implies.

### Medium

**F5 — `wizardCommand.ts:nextSteps`: teaches redundant flags.** Prints `--adapter fts5 --profile <path>` on both closing commands, though `paths.ts:ingestProfilePath` already prefers the user profile and `fts5` is `DEFAULT_ADAPTER`. *Recommendation*: emit the bare `dp-gnosis search "<keywords>"` when `adapter === DEFAULT_ADAPTER && profilePath === userProfilePath()`, and keep the explicit form only when the instance is non-default.

**F6 — `wizardCommand.ts:interview`: `instanceRefusal` runs after the first question.** The `alreadyExists` half depends only on `userProfilePath()`. *Recommendation*: hoist that half above `askDataRoot`; keep the `alreadyOccupied` half where it is, since it needs the chosen root.

**F7 — `wizard/rerankFlow.ts:fetchModel`: one wrong wording for four different failures.** `the download did not verify and was discarded` is printed for disk-space refusals and HTTP errors alike. *Recommendation*: print `downloadFile`'s error verbatim under a neutral lead (`the download did not complete: …`), since `download.ts` already words each cause correctly.

**F8 — `wizard/rerankFlow.ts:serveModel` / `resolveRunMode` / `backend.ts:BACKEND_KINDS`: two of three detected backends are never consumed.** A machine with `llama-swap` or `ollama` is told no server was found and handed a `llama-server` command line. *Recommendation*: either drive `llama-swap` (it accepts the same model file) or narrow `detectBackends` to what is actually used and reword `NO_BACKEND` to say `llama-server` specifically, so the message cannot contradict the machine.

**F9 — `wizardCommand.ts:CANCELLED_TEXT` → `EXIT_PARTIAL`.** A user cancellation and a failed build step both exit 3; `outcome.ts` defines 3 as *partial output produced*, and a cancellation produces none. README:94 documents the behaviour but the semantics still collide. *Recommendation*: return `EXIT_OK` for a deliberate cancel (nothing was asked for, nothing failed), or introduce a fourth documented code. This is a contract decision, not a bug fix — raise it with the owner rather than changing it unilaterally.

**F10 — `wizard --json` produces unparseable stdout.** `cli.ts:renderJson` applies to every command, and `help.ts` documents `wizard command, profilePath, indexState` as JSON keys — but `wizard/prompts.ts:terminalPrompter` writes the whole interview to `process.stdout` directly (`write`), bypassing `CliResult`. So `wizard --json` emits prose followed by JSON. README:67 separately claims `wizard` honours **no** flags, contradicting `help.ts:125`. *Recommendation*: refuse `--json`/`--format` on `wizard` via `SCOPE_CHECKS` (it is interactive by definition) and drop the wizard row from `help.ts`'s JSON-keys block, or route `prompter.say` through a sink the command owns. The refusal is simpler and matches README.

**F11 — `src/cli/retrieveCommand.ts` (2 254 lines) holds retrieval policy, not just presentation.** `firstPassK` / `cappedPoolK` implement the served pool floor `max(k, RERANK_K_INIT)`; `applyFloor`, `applyBudget`, `confidenceOf`, `resolvePrf`, `trimmed` and `arranged` are all retrieval semantics. Consequently `src/index.ts:search` and `src/mcp/server.ts:runAnswer` reach them only by building an argv string and re-parsing JSON.
*Why*: this is the modularity expectation's core. The single-owner argument in `index.ts`'s docblock is sound — a parallel implementation *would* drift invisibly — but the fix chosen (make everyone a CLI client) means the library API's type safety is restored only by two `as GnosisAnswer` assertions (`index.ts:asAnswer`, `mcp/protocol.ts:asAnswer`) guarded by one- and two-field runtime checks, and `src/api.d.ts` is a hand-written declaration nothing verifies against the producer (`answerCommand.ts:payload`).
*Recommendation*: no rewrite. Extract the **policy** functions (`firstPassK`, `applyFloor`, `applyBudget`, `confidenceOf`) into a `src/retrieval/` service module that both `retrieveCommand.ts` and a future typed `search()` call, leaving flag parsing and the three renderers in the CLI file. That keeps one owner per behaviour while removing the string round-trip as the *only* path to it. This is a proposal, not an applied change.

### Low

**F12 — `locations.ts:repoRootRefusal` does not name `wizard`.** The first refusal an installed-package user meets points at `init` alone, though `wizard` is exempted from the same check by `cli.ts:ROOTLESS_COMMANDS` and is the documented first run. One-word fix.

**F13 — `help.ts:helpText` command order.** Lists `init` before `wizard`; `cli.ts:COMMANDS` and README both lead with `wizard`. Cosmetic, but `--help` is where a stranger looks first.

**F14 — `wizard/rerankFlow.ts:fetchModel` quantisation matching is a substring `find`.** `F16` can match `mmproj-f16.gguf`; a split GGUF matches part 1 and then verifies cleanly against its own size and `lfs.oid`. Low risk today (two pinned repositories, sizes read 2026-08-30), but the failure mode is "downloads, verifies, will not load".
*Recommendation*: require the label to be delimited (`-Q4_K_M.gguf` / `.Q4_K_M.gguf`) and refuse a listing where more than one file matches, naming both.

**F15 — README:76 `search` "Honoured flags" is incomplete.** The Commands table omits `--type`, `--domain`, `--max-tokens`, `--min-relevance`, `--prf*`, `--max-per-doc`, `--flat`, `--field-weights` from the `search` row, although the Flags table marks each as **`search` and `ask`**. Other rows in that table read as exhaustive. *Recommendation*: append "…and every flag the table below marks **`search` and `ask`**" to the row.

**F16 — `DP_GNOSIS_EMBED_URL` (`src/config.ts`) is documented nowhere.** Read by the code, absent from README and CONFIGURATION.md.

**F17 — `screen.ts:section` counters reappear during amend.** Re-running `askTypes` from the amend menu reprints `3 / 6 · How documents are labelled` after the user has reached the summary. Cosmetic; a suppressed counter during amendment would read better.

## Strengths — what should not be changed

1. **Plan-before-write (`wizard/plan.ts`).** The wizard's decisions are a pure function returning a value that can be rendered, refused and dropped. This is what makes `Ctrl-C` safe, what makes `review`'s amend loop a three-line recursion, and what makes the whole interview testable without a terminal.

2. **The closing proof (`wizardCommand.ts:verify` + `STATE_REMEDY`).** The wizard runs `index` as part of the same step as `ingest`, then runs one real `search` and reads `indexState` back. This closes the first landmine in `handbook/GNOSIS-GUIDE.md` — an `ingest` that exits 0 over an index that will refuse every query — by construction rather than by advice. `blocked()` distinguishing "ingest refused everything" from "ingest reported skips" by counting atoms on disk rather than by the exit code is exactly right.

3. **Probe-before-configure (`rerankFlow.ts`, `setupCommand.ts`, `download.ts`).** Nothing about a reranker is written on the strength of an HTTP 200 or a completed download. `download.ts` promotes a `.part` only after size **and** sha256 verify, restarts from zero when a server ignores a `Range` request, and states the weaker guarantee honestly when a repo publishes no `lfs.oid`. `models.ts` refuses broken repositories by name and records the measurement that excluded `Q2_K` for the 0.6B only.

4. **Advice that routes instead of quoting (`wizard/advice.ts`).** Every claim is qualitative and names its owner (`handbook/GNOSIS-BASELINES.md`, `CONFIGURATION.md` § 9); the file's docblock states the rule and its reason. `timingLines` measures the machine in front of the user rather than quoting a constant, and labels the pool projection as a projection. This is the correct response to `GNOSIS-RULES.md` § Volatile facts.

5. **Refusals that carry a working remedy.** `alreadyExists` names `DP_GNOSIS_CONFIG_HOME` rather than `DP_GNOSIS_DATA_HOME` and its docblock explains that the obvious remedy would not work. `repoRootRefusal`, `NO_TTY`, `noServerOutcome`, `emptyProblem`, `prfAdapterError` all name the correction, not just the fault.

6. **`cli.ts` error containment.** `contextResult` and `withContext` convert malformed-config and profile-vocabulary errors into exit 2 with the loader's own message; both docblocks record that these previously escaped as Node stack traces with `dist/` paths. `main.ts` is 21 lines and does nothing but bind values to the process. No stack-trace-to-user path remains in the reviewed surface.

## Resolved landmines — FIXED / CLOSED / GATED

| Landmine | Mechanism | Resolution |
|---|---|---|
| **A reranker with no usable rank head returns HTTP 200 and NOISE** — GATED | `jina-reranker-v3` AND `v3.5` load, serve `/v1/rerank`, and return well-formed scores carrying no ranking signal — both ranked a chocolate-cake recipe above a BM25 passage. Root cause is not an unsupported pooling type: **the ranking head is ABSENT FROM THE GGUF ENTIRELY** (measured on both local files — arch `qwen3`, `pooling_type` KV absent, **310 tensors, NO `cls` / `score` / `rank` / `classifier` / `pooler` tensor**; Jina ships the MLP projector as a separate `projector.safetensors`), and the models are **listwise**, so the pairwise `/v1/rerank` shape is wrong by construction. **NO FLAG AND NO BUILD FIXES IT** — explicit `--embedding --pooling rank --reranking` gives BYTE-IDENTICAL output. They also device-lost the GPU (`vk::Queue::submit: ErrorDeviceLost`) on every real arm — the RADV class that forces gemma to ROCm-only, so retrying on Vulkan risks the desktop, not just the run. Worst failure class: plausible data, no error. `docs/research/2026-08-16-2123-jina-reranker-v3-score-scale-vs-broken.md` | **The bench REFUSES the arm**: before a dataset's first rerank call it scores a fixed relevant/irrelevant pair and FAILS with `dp-gnosis-bench/rerank-probe-failed` unless the scores DIFFER and the relevant one wins. Reference separations: bge `+2.07` vs `−11.00`; qwen3 `0.998` vs `~1e-05`. **TWO broken signatures**: *near-zero, no signal* (jina v3/v3.5 — `1.96e-07` vs `2.94e-07`) and *CONSTANT* (`mxbai-rerank-large-v2` — the SAME score to 16 decimals across unrelated documents; it varies with the QUERY, invariant to the DOCUMENT). The constant case is more dangerous: equal scores leave the first-pass order essentially intact, so a run looks like *"reranking barely helped"* instead of failing. A directional pass alone does NOT clear a model — jina v3 passes it. MUST still hand-probe any NEW model with ≥2 documents plus hard negatives |
| **A non-`fts5` adapter that indexed NOTHING passed the soundness gate** — GATED | The gate probed the **fts5** index whatever adapter was under measurement, so a `lancedb` / `minisearch` index holding nothing recorded all-zero metrics as data — the recurring failure class sitting directly under the adapter campaign | The bench REFUSES the run on the **MEASURED** adapter's port: `dp-gnosis-bench/port-index-not-ready` unless the opened port reports `indexState === 'ready'`, and `dp-gnosis-bench/port-retrieved-nothing` if the port returns nothing across a sample of the dataset's own topics. The gate changes what a run REFUSES, never what it measures — a recorded `fts5` arm re-runs bit-identical |
| **The gold-aware dedupe was INERT on the PRODUCTION path** — CLOSED 2026-08-19 (T2.1e) | `ingest.ts` `goldOf` reads `options.goldIds`. The BENCH passed them; `cli/ingestCommand.ts` did NOT, so a production `npm run gnosis -- ingest` kept whichever mirror of a byte-identical group sorted first. It never bit while the vault predated the dedupe (its atoms dir held BOTH copies and the bench deduped the projection itself) — **the first real re-ingest destroyed 50 of 382 gold judgments across 19 topics, 7 losing all gold** | `ingestCommand.ts` passes the union of every `golden-set*.json` in the engine's own `golden/` dir. **A fix verified in the bench does NOT protect a corpus the bench merely READS** — `datasets.json` derives `vault` from the production atoms dir, so the CLI ingest runs FIRST and its output is what the bench can measure. Verify a corpus-hygiene fix at the layer that WRITES the corpus |
| **Benchmark output inside the measured corpus** — CLOSED 2026-08-19 | `docs/analysis/2026-08-09-1126-adapter-outputs/` holds machine-generated per-query dumps quoting the GOLDEN QUERY TEXT verbatim, so they match the benchmark's own queries trivially and outrank the real answers. Measured when the `docs/` root went live: **250 atoms took 188 of 600 top-10 slots (31.3 %) across 42 of 60 topics** (all ten on `q-022`), dropping `vault` nDCG@10 0.4721 → 0.3019 while R@100 moved only −0.0082 | Excluded by path, same class as `docs/benchmarks/`. **Benchmark output MUST NOT sit in the corpus the benchmark measures.** A metric alone cannot detect this — `rbpResidual` rose, which reads as thin judgments; only NAMING the documents that displaced gold distinguished it. `07-plan.md` § 6.19 |
| **The regression gate can report a REGRESSION across a corpus change it cannot see** | `SCALE_FIELDS` guards `corpusBytes` / `corpusLines`, which describe the SOURCE `corpus.jsonl` — NOT the atoms indexed. `atomCount` was unguarded. Measured at `6f87ca08`: T2.1's dedupe removed 296 `vault` and 40 `nfcorpus` atoms at ingest while both guarded fields stayed byte-identical, so `compare.ts` subtracted and the gate declared `vault` −0.0921, p=0.0005 | CLOSED by T2.1b — `atomCount` is a `SCALE_FIELD` as of 2026-08-19, so that pair now REFUSES instead of subtracting. A gate exit 4 following ANY ingest-side change is a scale artefact until proven otherwise, and every row recorded BEFORE T2.1b must still be read under that rule. **MUST compare `atomCount` on the two rows before believing a gate regression.** "Cannot compare" is the truthful verdict: a NEW baseline is owed (§ Session rules 8), not that quality moved |
| **Stale materialized documents contaminate a corpus** — FIXED | `materializeCorpus` only ever WROTE `<docid>.md`, never removed one dropped from `corpus.jsonl`. `vault-hu` carried **114 ghosts** for days. Ghosts occupy ranks and can never be credited — worth **+0.05 to +0.075** nDCG@10, more than every treatment effect on that corpus, and it **inverted the campaign's conclusions** | Materialization prunes, and a doc-count/`corpusLines` mismatch REFUSES before ingest. On any old row: `atomCount` far above what `corpusLines` can produce = contaminated |
| **`docs/` was invisible to retrieval** — FIXED | It matched no corpus root and no domain prefix, so it failed at the SCOPE gate and was not even reported in `skipped[]` | `docs` is a corpus root as of T2.1, with a `docs/` domain rule and per-subtree type rules — usable ONLY together with the profile's three `excludePaths`: `docs/tmp/` (12 211 files) and `docs/benchmarks/` (10 386) are machine output, and `doc/_meta/corpus-digest.md` is a navigation artefact carrying one line of vocabulary from every document, so it scores on almost any query. All three are dropped by path before anything is read. A directory entry MUST end in `/` — the match is a plain `startsWith` prefix, so `docs/benchmarks/` MUST NOT swallow the authored sibling `docs/benchmarking/`. `packages/gnosis/AUTHORING.md` § 1 |
| **A crash destroyed every dataset that had already succeeded** — FIXED | The run buffered everything and wrote once at the end; a Tier-1 run OOM'd on its seventh dataset after 67.5 min and six completed datasets were recorded nowhere | Each dataset's row, TSV and run file are written as it finishes, artefacts BEFORE the row naming them — a crash leaves an unreferenced file, never a row pointing at a missing one |
| **A corpus above 0.5 GB could not be read at all** — FIXED | `readJsonl` (`beir.ts`) and `corpusChecksum` (`report.ts`) each read a whole corpus into ONE string; Node's max string is ≈0.5 GB | Both stream line-by-line. The bench runs with an **8 GB heap** (`bench.sh` is its single owner); the 4.19 GB default is not enough for the largest Tier-1 corpus |
| **Sweep stem collided at minute resolution** — FIXED | Two sweeps in the same minute at the same sha wrote the SAME JSON, `.md`, `.svg` and per-cell TSVs — last writer won, no error | Stems are millisecond-resolution throughout. Parallel fan-out is safe by construction; the >60 s stagger rule is retired |

## Closed harness gaps

| Gap | Consequence |
|---|---|
| **Provenance recorded the REQUESTED depth, not the effective rerank pool** — CLOSED 2026-08-18 by `rerankPool` | `firstPassDepth` (`run.ts`) resolves the first pass as `rerank ? Math.max(depth, RERANK_K_INIT) : depth`, but the history row stored `depth: options.depth`. So a `--depth 20 --rerank` run whose pool was actually 100 recorded `depth=20`, and two runs with DIFFERENT effective pools carried IDENTICAL scale provenance — `compare.ts` would subtract them as a like-for-like treatment delta. Verified 2026-08-18: raising `RERANK_K_INIT` 20 → 100 (T1.1) silently deepened every bench rerank arm below depth 100 with no provenance change. Fixed by stamping `rerankPool`. **Rows written BEFORE the field**: re-derive as `max(depth, RERANK_K_INIT-at-that-sha)` — `compare.ts` backfills exactly that, with `20` as the pre-`92d683e2` floor |
| **A rerank pool smaller than `RERANK_K_INIT` needs `--rerank-pool`** — CLOSED 2026-08-18 | `firstPassDepth` is still `max(depth, RERANK_K_INIT)` when no pool is named, so with `--rerank` on, `--depth` alone can only RAISE the pool — and `92d683e2` raised the constant to 100. `--rerank-pool <n>` sets it explicitly and bypasses the floor, so the depth-curve result behind the skill's `-k` ≥ 5 rule is reproducible again. **MUST NOT quote a small-pool rerank arm measured after `92d683e2` WITHOUT the flag** — those recorded pool 100 whatever `--depth` said |
| **A cutoff deeper than the run was reported as a measured number (G10)** — CLOSED 2026-08-18 by T0.2 | `recall100` on a `--depth 20` row was never recall@100 — scoring is cut at `depth`, so it was recall@20 under the wrong name, and `compare.ts` would subtract one from a genuine R@100. `measurableRecallAt` now returns `undefined` when `k > depth`, and the per-topic TSV serializes it EMPTY rather than `0`. **Every row recorded BEFORE the fix still carries the misleading column** |
| **No cross-adapter fusion** — precondition CLOSED | Fusion still exists only as reranker↔first-pass within one adapter, but its blocker is gone: `results/runs/*.trec` persists the per-topic **rankings**, so two adapters' orders can be fused, error-analysed or re-scored under a new metric **with no re-run** |

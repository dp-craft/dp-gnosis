## What dp-gnosis is (and is not)

| | |
|---|---|
| **Is** | Lexical BM25 over a vault of markdown **atoms** — one document chunked into frontmatter-tagged units. No server, no network at query time |
| **Is NOT** | **Semantic retrieval AS SHIPPED.** `lancedb-vec` / `lancedb-hybrid` were built and measured in Phase D but are not deployed. The old reason given here — *"they lose to query rephrasing"* — is **FALSIFIED on both halves** (§ Settled): rephrasing is INERT at prompt v2, and dense measures **+0.0358 nDCG@10 (p=0.0001)** on `arguana`, where its sign flips positive. The live reason is narrower: every dense win is FIRST-STAGE and unproven through the reranker, and it costs an embedding server, a 1.1 GB model, a vector column, a cache and a fusion path. The four lexical adapters remain the only production routes; `lancedb` itself is full-text BM25 only, frozen, no vector column |
| **Optional hops** | `--rerank` (cross-encoder over HTTP at `127.0.0.1:9292`) · `--rephrase` (chat model rewriting the query before the first pass, measured inert). Both opt-in |
| **The one lever ON by default** | **`--prf`** — RM3 pseudo-relevance feedback, NOT a network hop, ON on the shipped profiles since 2026-08-22. Pure SQLite over fts5's own scorer; `--no-prf` turns it off. Every expanded run reports the cell it used |
| **Largest measured quality lever** | **Query phrasing**, not adapter choice. MUST rewrite a question to keywords before every `retrieve`. Rule + language split: `packages/gnosis/QUERYING.md` § Query rephrasing. Measured effect: `GNOSIS-BASELINES.md` |

## Architecture — the path lives in GNOSIS-DATA-FLOW.md

**`GNOSIS-DATA-FLOW.md` is the SINGLE OWNER of the pipeline** — prose flow, diagram, per-stage contracts, the typed hops, where each analyzer / BM25 / index artifact lives, and which hop a change belongs to. **Read it before changing analysis, chunking or the rerank protocol.** This section carried a second copy once; that is how the `fts5` column count went stale in one of them.

The shape, so this file reads without the jump:

| Stage | What happens |
|---|---|
| Ingest | markdown → heading-bounded atoms in `atomsDir`; `writeManifest` stamps `corpus-manifest.json` into that directory's PARENT |
| Index build | `prepareDataset` builds the artifact the CHOSEN adapter needs; `openPort` REFUSES an index prepared for another adapter |
| Retrieve | `createPort(adapter, atomsDir, indexPath)` → `port.retrieve(RAW query text, {k})`. The port passes a `string`, so **every adapter analyses the query itself** |
| Rerank (opt-in) | `--rerank` → cross-encoder over HTTP at `RERANK_DEFAULT_URL`, then `fuseRanking` against the first-pass order |
| Rephrase (opt-in) | `--rephrase` → chat model rewrites the query BEFORE the first pass; a refusal retrieves RAW and exits 3 |

### Adapters — all lexical

`ADAPTER_NAMES` holds **seven** entries (four lexical + three dense) and `DEFAULT_ADAPTER = 'fts5'` (`cli/adapter.ts`), asserted equal to the bench default by `tests/defaults.test.ts`. The sweep is fixed at `linear`, the only tunable one. **Corrected 2026-08-18** — was `['linear','fts5','minisearch','lancedb']` / `DEFAULT_ADAPTER = 'linear'`. Read the constant, never this sentence.

| Adapter | Role | Tunable? |
|---|---|---|
| `linear` | Reference BM25 in TypeScript. Exact but slow — `scanCorpus` re-reads the corpus every retrieve unless `cacheCorpusScan`, set ONLY by the sweep | **Yes** — `BM25_K1=1.2` / `BM25_B=0.75` (`linearScanAdapter.ts`) |
| `fts5` | **Production.** `FTS_COLUMNS` (`config.ts`) declares **seven** columns — `body, short, long, doc_desc, keywords, entities, questions` — and `--field-weights` merges over `DEFAULT_FIELD_WEIGHTS` (`body: 1`, every enrichment column `0`). Served ranking is body-only **by weight, not by schema**. That zero default is why the schema change moved no recorded number: `vault`, `vault-hu`, `scifact` re-ran **byte-identical**. Tokenizer `unicode61`; `stemText` applied index- AND query-side. **Corrected 2026-08-24** — was *"SINGLE-COLUMN … column weighting impossible without a schema change"* | **Partly** — k1/b compiled into SQLite with no setter; per-column weights ARE tunable via `--field-weights` |
| `minisearch` | Optional dep — its own defaults, tokenizer, field setup | boost / fuzzy / prefix all unset |
| `lancedb` | LanceDB full-text (BM25) ONLY — a v2-readiness probe, **no embeddings, no vector column**, deliberately FROZEN so its baseline stays reproducible. `FTS_INDEX_OPTIONS` sets `maxTokenLength` explicitly; unset, LanceDB silently DROPPED every token ≥40 chars, which `fts5` keeps | FTS index options in `lanceDbAdapter.ts` |
| `lancedb-vec` | **Dense only** — `bge-m3` over the RAW body, exhaustive cosine (`bypassVectorIndex()`, no ANN). The Phase D control. **Measured HARMFUL on English** (−0.1621 nDCG@10, p=0.0001) | embedding model / pooling, served by llama-swap |
| `lancedb-hybrid` | **Dense ⊕ lexical** via `fuseLegs` (`rerank.ts`) — never LanceDB's `RRFReranker`. At `--hybrid-weight 0.25` it TIES `fts5` on both corpora; at the inherited 0.5 it looked like an English regression. Still loses to query rephrasing. NOT shipped | **`--hybrid-weight`** — SWEPT; best 0.25 English, flat 0.25–0.75 Hungarian |
| `lancedb-hybrid-full` | Same fusion, reranker offered the whole ~1.6×`k` union instead of the fused top-`k`. Raises recall as forecast, converts none of it (null on all three corpora) at 1.64× rerank cost. Recorded evidence, NOT a route to use | `--hybrid-weight`, as above |

**MUST NOT read an adapter comparison as a scorer comparison.** They differ in BM25 parameters, tokenizer AND field setup simultaneously, so the suite answers *"which implementation performs best as shipped"*, never *"which scorer is better"*. `linear` additionally tokenizes `frontmatter.title` where `fts5` indexes `atom.body` alone; the offset **flips sign** across corpora (+0.0192 bright-passages, −0.0384 bright-biology, **+0.0438** `vault-hu`), and the title-field hypothesis was tested by direct experiment and **refuted** as its explanation.

### Rerank — the fusion RULE is a parameter, the rest are shipped constants

| Constant (`config.ts`) | Value | Note |
|---|---|---|
| `RERANK_DEFAULT_URL` | `http://127.0.0.1:9292` | NOT caller-settable |
| `RERANK_K_INIT` | **100** | was 20 before `92d683e2`. NOT caller-settable |
| `RERANK_RRF_K` | 20 | |
| `RERANK_RRF_WEIGHT` | **0.75** | was 0.5 until 2026-08-19 (T1.5c-adopt, owner-approved on a pre-registered held-out arm). **Every row recorded before that carries 0.5** |
| `HYBRID_DENSE_LEG_WEIGHT` | 0.5 | the hybrid route's dense-leg share |

Changing `K_INIT` or the URL means editing `config.ts` and taking a **NEW baseline**.

**`HYBRID_DENSE_LEG_WEIGHT` is its OWN binding.** It reads 0.5 — the value every recorded `lancedb-hybrid` row was measured at — but is no longer derived from `RERANK_RRF_WEIGHT`, so tuning the reranker's RRF weight can no longer move the leg fusion as a side effect. Two different fusions; MUST NOT be conflated. Deliberately unchanged despite `w=0.25` measuring better on English: the route is not shipped, and moving it would make new rows non-comparable with every recorded one.

**The fusion rule CAN be selected by name** — two presets, a two-member discriminated union, deliberately not a plugin registry:

| Preset | Rule | Use |
|---|---|---|
| `shipped` (default) | RRF over `RERANK_RRF_K` / `RERANK_RRF_WEIGHT`. **NOT bit-identical across 2026-08-19** (weight 0.5 → 0.75), so a `shipped` row recorded before that does NOT reproduce today. `compare.ts` backfills an absent `rerankWeight` to 0.5 and labels the pair `ARM COMPARISON` | what the product serves |
| `beir-ce` | **Pure replacement** of the first-pass order by the reranker's | what the published BEIR BM25+CE baseline does — use it against published numbers |

Both rerank the **same pool at the same depth for the same cost**; they differ ONLY in how the two orders combine. `resolveRerankFusion` refuses an unknown name rather than falling back — a silent fallback would publish a number under the wrong label. `rerankProfile` / `rerankWeight` are `TREATMENT_FIELDS`, so `--compare` labels a fusion change `ARM COMPARISON`.

**`RERANK_K_INIT` is a FLOOR, not a cap.** `retrieveCommand.ts` resolves the first pass as `Math.max(request.k, RERANK_K_INIT)` — pool `max(k, 100)` since `92d683e2`. The constant binds every caller asking for FEWER than 100, now the common case; `-k 200` reranks 200. MUST NOT read *"the reranker sees `k`"* as a property of the pipeline. Below the floor the pool IS the floor, at ~12 s/query (BASELINES § Serving path).

RRF is `score(d) = w/(K + rank_rerank(d)) + (1−w)/(K + rank_bm25(d))`.

Three standing rules from that episode:

| Rule |
|---|
| MUST re-probe the window before raising `RERANK_DOC_MAX_CHARS`, lengthening the query, or changing `-np` — read it off the server, never off `-c` or the display name |
| The over-window refusal above 8192 is a `-b`/`-ub` batch **`server_error`**, NOT the `exceed_context_size_error` `singleRerank` bisects on. Inert while `ATOM_MAX_CHARS = 4000` (≈2840 tokens worst case) caps every document below it; a real gap the moment anything exceeds 8192 |
| `~/.config/llama-swap/config.yaml` carries a `GENERATED by generate.py` header and **had been hand-edited** to `-np 6` while `generate.py:241` still emitted `-np 1`. MUST change the generator and regenerate — a hand edit drifts silently, and that cost a day |

**Both scores survive the fusion.** A reranked `RetrievedAtom` carries `firstPassScore` and `rerankScore` beside `score`; `score` still holds the FUSED value and the order is still taken from it. Ranking is **byte-identical** with and without the fields — `tests/retrieveExplain.test.ts` pairs the reranked order against `fuseRanking` itself as the oracle. Both are ABSENT on a non-reranked run rather than defaulted, so their presence is what says a rerank happened; the CLI also reports `poolSize`, the first-pass size the cross-encoder actually scored. Before this, `rerankAtoms` overwrote the first-pass score with the fused one and discarded the cross-encoder's own, leaving a caller unable to tell an atom the reranker AGREED with from one it rescued.

**`rerankScore` is the field an abstain rule should read** — the only one with an absolute scale, and since T3.1a that scale is MEASURED per model. `RERANK_CALIBRATION` (`config.ts`) maps a served reranker to `identity` or `sigmoid`; `calibrate(model, raw)` (`rerank.ts`) returns a probability, or `undefined` for a model with no measured scale. No default — guessing is silent in both directions (`identity` on a logit model yields `p = 5.06`; `sigmoid` on a probability squashes everything into [0.5, 0.73]). Probed 2026-08-19 over one query with a relevant / partial / unrelated document:

| Model | Scores | Scale |
|---|---|---|
| `qwen3-reranker-4b` | 0.99972 / 0.32028 / 0.0000039 | probability |
| `qwen3-reranker-0.6b` | 0.99973 / 0.94059 / 0.00012 | probability |
| `bge-reranker-v2-m3` | 5.0632 / −0.1369 / −10.9998 | logit — a negative score cannot be a probability, so this is proved, not assumed |
| `ettin-reranker-1b-v1` | 2.4520 / 0.8657 / −0.2419 | logit, same proof |

**The BANDS are still uncalibrated, and the CLI is built to say so.** `retrieve` reports `confidence ∈ {none, weak, ok}`: `none` = nothing delivered · `ok` = a floor is in effect AND the top-1 calibrated `p` clears it · `weak` = everything else. **CORRECTED 2026-08-29** — the earlier claim that *"`--min-relevance <p>` is the only floor and it is OPT-IN, so `ok` is unreachable on a default run by design"* is STALE: `retrieveCommand.ts:verdictFloor` reads `budgeted.minRelevance ?? ABSTAIN_FLOOR`, and `config.ts:ABSTAIN_FLOOR = 0.4` exists, so a DEFAULT `--rerank` run reaches `ok` whenever its top-1 calibrated `p` clears 0.4 (observed on this tree). `--min-relevance` now only OVERRIDES that floor. The default floor is strictly a VERDICT input — every DROP path still reads `minRelevance` alone, so it changes what a run CLAIMS and never what it delivers. The floor is strictly subtractive — applied after the rerank and the `-k` slice, it never reorders, never promotes an atom from deeper in the pool, never moves `poolSize` — and it REFUSES (exit 2) on an out-of-range value, without `--rerank`, or on a reranker absent from the table.

**Fusion exists in exactly ONE place**: `fuseRanking` (`rerank.ts`), fusing the reranker order with the first-pass order of a **single** adapter. There is no cross-adapter fusion. The bench passes a fusion NAME through `engine.ts` and MUST NOT reimplement fusion, or the suite would stop measuring the real engine.
